## Gaps and recommended probes

- Request-side bounds: the core files inspected expose only CLIENT-side response caps. Java's `MAX_REQUEST_BODY` (1 MiB) and `MAX_BATCH_SIZE` (100) are CONSTANTS whose enforcement lives in generated adapters that were not inspected. Probe oversized request bodies and 101-entry batches against a generated server.
- Nesting depth: no runtime sets an explicit depth limit in the inspected files. Probe deeply nested JSON (e.g. 10k levels) to determine effective parser limits (Go `encoding/json` internal ~10000; Java Jackson/Gson defaults; C# System.Text.Json default 64).
- Duplicate keys: probe `{"id":1,"id":2,...}` and duplicate by-name params across all three runtimes to confirm last-wins vs reject; the C# param-level first-wins behavior (Server.cs:263-271) is not JSON-level detection.
- Numeric IDs >2^53: probe ids `9007199254740992` and `9007199254740993` to check precision loss and request/response id matching (Go's float64 conversion, transport.go:43-59).
- Batch-size caps: confirm whether Go/C# implement any batch cap at all, and locate Java's actual `MAX_BATCH_SIZE` check site.
- C# server-side caps: locate the generated HTTP server adapter (request body limit, response serialization limit) and `Client.ValidateEnvelope` referenced at Transport.cs:193.

## Residual

- Go: generated HTTP adapter (request decode, batch loop, response serialization) not inspected; stdlib depth/duplicate behavior inferred, not verified by a test.
- Java: generated server/client adapters (JSON parser config, request-size and batch enforcement) and Validation.java numeric ranges not inspected; only HttpLimits.java and Server.java were read.
- C#: generated HTTP server adapter and Client.ValidateEnvelope (Transport.cs:193) not inspected; only Transport.cs and Server.cs were read.
- No tests were run and no runtime behavior was empirically verified; all entries are static-read findings. A final `git status` verification was not run in this pass; the commit output is the confirmation of what was written.
