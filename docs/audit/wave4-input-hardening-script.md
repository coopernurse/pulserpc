## Gaps and recommended probes

- **Nesting depth:** No explicit JSON nesting-depth bound was found in any of the eight inspected files. Decoders rely on the host parser (`json.loads` / `JSON.parse`). Probe each runtime's HTTP adapter with deeply nested `params` to see whether a native recursion limit is reached and how it is surfaced. The adapter/entrypoint layer was not inspected for any runtime.
- **Duplicate keys:** No runtime explicitly detects or rejects duplicate JSON keys; Python/Python2 stdlib `json.loads` and Node `JSON.parse` use last-wins semantics. Probe envelopes with duplicate `id`, `method`, `jsonrpc`, and `params` keys and confirm the resulting value is acceptable. (Static inference only; not executed.)
- **Numeric ID >2^53:** All four accept >2^53 numeric IDs without a magnitude bound. Python accepts any finite int/float (`server.py:35-38`); Python2 explicitly accepts large `long` values as a documented R24 carve-out (not a defect); ts-node/ts-cjs accept any JS `number` (lossy precision above 2^53). Probe ID echo fidelity and cross-request collisions at these magnitudes.
- **Batch size:** Only Python has a confirmed cap (100). Python2, ts-node and ts-cjs `Server.call` handle a single request and reject arrays in the inspected files, so any batch handling/cap resides in the HTTP adapter layer, which was not inspected. Probe >100-element batches across all four runtimes.
- **Request-body (inbound) cap:** Python2 exposes an advisory 1 MiB `DEFAULT_MAX_BODY_SIZE` (`server.py:22`) but it is not enforced in the inspected file; Python has no inbound cap constant in the inspected files; TS inbound caps are unknown. Probe oversized POST bodies and inspect each HTTP adapter. Response (outbound) caps are confirmed at 10 MiB for all four.
- **Not inspected:** HTTP adapter/server entrypoints, `validation.ts`/`validation.py`, generated code, and the Go conformance harness. These may contain additional or compensating bounds.

## Residual

- Only two files per runtime were inspected; no HTTP adapter/envelope-decode entrypoint was examined for any runtime, so batch-size handling and inbound body caps for ts-node, ts-cjs and Python remain UNVERIFIED.
- No tests or runtime probes were executed; all findings are static-analysis observations from the cited files only.
- Numeric-ID >2^53, duplicate-key and nesting-depth behavior are inferred from parser defaults / type checks, not observed at runtime.
- Python2 batch absence and large-`long` ID acceptance are documented legacy carve-outs and are not reported as defects.
