which emits the literal text into the generated adapter. Caps implemented only in a
runtime transport already surveyed are flagged as such, not reported as new.

## Findings

Runtimes that **actually enforce both caps at the generated adapter layer**:
- **Go** — body via `http.MaxBytesReader` (go_client_server.go:969) and batch via `len(requests) > maxBatchSize` (993); call site `handleRequest`.
- **C#** — body via `HttpTransport.ReadLimitedAsync` (csharp_client_server.go:866) plus content-length precheck (856) and batch via `batchLength > MaxBatchSize` (902); call site `HandleRequest`. Streaming cap itself lives in the already-surveyed runtime transport `HttpTransport`.
- **TypeScript (ts-node and ts-cjs, shared template)** — body via `size > MAX_BODY_SIZE` (ts_client_server.go:2190) and batch via `data.length > MAX_BATCH_SIZE` (2237); call site `TestRPCHandler.handle`. Emitted filename for both module styles is `server.ts` (ts_client_server_test.go:357/407).

Runtimes enforcing caps only partly at the adapter layer (constant/check split with runtime transport):
- **Java** — the adapter performs the comparisons and dispatches the error (java_client_server.go:1054, 1055, 1063, 1104), but the constants `HttpLimits.MAX_REQUEST_BODY` / `HttpLimits.MAX_BATCH_SIZE` and the bounded-read implementation live in the already-surveyed runtime transport `HttpLimits`. No new runtime-side cap found.
- **Python** — body cap in generated `TestRPCHandler` (python_client_server.go:1030/1040, emitted to `test_server.py`); the generated adapter has no batch cap and delegates via `rpc_server.call` (python_client_server.go:1057), but runtime `pulserpc.server` enforces `DEFAULT_MAX_BATCH_SIZE = 100` with check `len(reqs) > self.max_batch_size` (server.py:23, 148). Batch cap confirmed at runtime, not in the generated adapter. **Production-server body cap: ABSENT.** The two paths named as "Python production HTTP server" are not HTTP servers: runtime `pulserpc/server.py` is a transport-independent `Server` (server.py:42-47) with no body reads and no `DEFAULT_MAX_BODY_SIZE` (server.py:23 is the batch cap only), and the generated production `server.py` template emits only `abc` service stubs (python_client_server.go:308-345). The `DEFAULT_MAX_BODY_SIZE` hint (python_client_server_test.go:1883) refers to the Python2 runtime constant at `pkg/runtime/runtimes/python2/pulserpc/server.py:22`; no such constant exists in the Python3 runtime. The only Python3 production HTTP handler, `examples/quickstart/python/my_server.py` (`PulseRPCHandler.do_POST`, 157-164), reads `self.rfile.read(content_length)` with no cap.

Runtimes **not applicable** at the adapter layer:
- **Python2** — no generated HTTP adapter exists: Python2 is a flag (python_client_server.go:91) that emits metadata + runtime only, and `server.py` / `test_server.py` are not generated (python_client_server_test.go:1906-1909, 1186). The 1 MiB cap is exposed as `pulserpc.server.DEFAULT_MAX_BODY_SIZE` and documented in `docs/languages/python/python2.md` (python_client_server_test.go:1881-1884). Body/batch caps in a generated adapter are N/A.

The only cap located outside a generated adapter (beyond the surveyed Java `HttpLimits` / C# `HttpTransport` helpers) is the Python runtime batch cap in `pulserpc.server` (server.py:148), reached from the generated handler through `rpc_server.call`.

## Residual

- Python2: no generated HTTP adapter exists (python_client_server_test.go:1186, 1906-1909); there is no `pkg/generator/python2_client_server.go` template. Body/batch cap enforcement at the adapter layer is N/A — row closed.
- Python production-server body cap: **RESOLVED — no inbound cap existed in the Python3 production path.** Evidence: runtime `pulserpc/server.py:42-47` declares a transport-independent `Server` with no HTTP/body handling; its only limit constant is `DEFAULT_MAX_BATCH_SIZE` (server.py:23), not `DEFAULT_MAX_BODY_SIZE`. Generated production `server.py` (`generateServerPyForNamespace`, python_client_server.go:308-345) emits `abc` service stubs only — no `BaseHTTPRequestHandler`, `do_POST`, or `rfile.read`. The `DEFAULT_MAX_BODY_SIZE` hint (python_client_server_test.go:1883) is the Python2 constant `pkg/runtime/runtimes/python2/pulserpc/server.py:22`. The sole Python3 production HTTP handler (`examples/quickstart/python/my_server.py:157-164`) read unbounded bodies. The generated test handler's 1 MiB cap (python_client_server.go:1030/1040) is test-only. **Remediation implemented:** runtime `pulserpc/server.py:31` declares `DEFAULT_MAX_BODY_SIZE = 1024 * 1024` (exported `__init__.py:50,99`) alongside `BodyTooLargeError` (server.py:34) and `read_request_body` with the enforcing check `if content_length > max_body_size` (server.py:42-52). The production HTTP handler binds `MAX_BODY_SIZE = DEFAULT_MAX_BODY_SIZE` (my_server.py:167) and rejects an oversized body with a JSON-RPC Invalid Request / "Request body too large" response (my_server.py:180-183) before any read, so the connection is not dropped. Boundary test in `tests/test_body_size_cap.py` (exactly 1 MiB accepted; 1 MiB + 1 rejected before read).
- Python generated-handler batch cap: confirmed absent in the adapter but enforced in runtime `pulserpc.server._call_batch` (server.py:148), reached via `rpc_server.call` (python_client_server.go:1057).
- Emitted filenames confirmed: Python test handler -> `test_server.py` (python_client_server_test.go:96) and server -> `server.py` (python_client_server_test.go:55); TypeScript -> `server.ts` for both ts-node and ts-cjs (ts_client_server_test.go:357, 407).
- Java `HttpLimits` and C# `HttpTransport` constant values / bounded-read internals were not re-read here (already surveyed in S3); only their call sites in the generated adapters were verified.
